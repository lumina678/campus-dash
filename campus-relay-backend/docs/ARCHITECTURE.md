# 系统架构

CampusRelay 采用模块化单体与领域分层结构。业务规则位于领域层，应用层负责编排用例，基础设施层提供数据库、缓存和消息实现，接口层提供 HTTP 与 WebSocket 接入。

## 模块依赖

```text
presentation / worker
          |
      application
          |
        domain
          ^
          |
   infrastructure
```

`relay-domain` 不依赖 Spring 或具体存储实现。基础设施通过端口实现接入 MySQL、Redis、RocketMQ、ShardingSphere 和 Sentinel。

## 抢单一致性

抢单链路采用多层约束：

1. Sentinel 对热点任务进行限流。
2. 应用层校验信用分和在途任务数量。
3. Redis Lua 原子扣减可用名额并处理幂等。
4. MySQL 使用带状态与版本条件的更新裁决最终结果。
5. 唯一索引防止同一轮次的重复占位与重复抢单。

Redis 保存可重建的运行时状态，MySQL 是最终事实来源。

## 资金模型

发布任务时，资金从发单人账户转入平台托管账户，同时记录双边流水和托管单。结算、退款和仲裁通过状态条件更新与唯一业务号保证幂等。

系统保留三类校验：

- 借贷方向总额平衡
- 账户余额快照与流水净额一致
- 托管单状态与结算、退款流水闭环

## 异步任务

需要精确定时的任务通过本地消息表与 RocketMQ 定时消息投递，后台扫描作为兜底。消息键、业务状态和数据库唯一约束共同保证重复消费不会产生重复结果。

## 缓存

任务详情使用 Cache Aside。更新完成后失效缓存，并通过延迟失效与一致性检查降低并发读写造成的旧值回填风险。布隆过滤器用于减少不存在任务的缓存穿透。

## 分片

任务链路按 `campus_id` 路由，账户与信用数据按 `user_id` 路由。需要跨分片的统计与对账由后台任务处理，避免在线请求执行全分片聚合。
